# AGENTS.md — AllesBuien

> Not running in the maintainer's software factory? Skip the beads and factory notes: file work as GitHub issues, run `bin/check-fast` and the tests nearest your change, and let CI run `bin/test`. [CONTRIBUTING.md](CONTRIBUTING.md) is the guide for that.

## Overview

AllesBuien is a native Omarchy weather application built as a Rust workspace with a Qt Quick/CXX-Qt desktop shell. It shows Buienradar current conditions, a five-day forecast, the rain expected over the next two hours in five-minute steps, an animated Dutch radar, and best-effort rain-soon notifications while following the active Omarchy theme.

## Run and verify

Run from the repository root:

```bash
bash .factory/gate          # the definition of done: wraps bin/test
bin/check-fast              # bin/test's text-only first step, ~0.25s
bin/build                   # release build
bin/install                 # bin/build and (cd pkgbuild && makepkg -f); prints Mode B's line, installs nothing
lefthook run pre-commit     # cargo fmt --check and bin/check-fast
just                        # lists the shortcuts for people over the above; never `just install`
```

`bash .factory/gate` is the definition of done and runs nothing but `bin/test`, which is the full workspace gate and the one CI runs — over twenty minutes from cold, because CXX-Qt regenerates C++. `bin/check-fast` is its text-only first step and what `lefthook` runs on every commit, so the hook can never hold a weaker opinion than the server. Tools are pinned in `mise.toml`, lefthook among them; run `mise install` first, which in the main checkout also writes the hook into `.git/hooks`, where every worktree shares it. In a linked worktree it leaves the hook alone, but `lefthook install` run by hand in one still rewrites it from that worktree's `lefthook.yml`, so run that in the main checkout only. A commit fails when the hook finds no lefthook, or one older than `mise.toml` pins: that is the machine's to fix, so say so in your report rather than skipping the hook with `--no-verify` or `LEFTHOOK=0`.

Do not change `.factory/gate` or any path listed in `.factory/protected` — a branch that touches one cannot be approved without a human reading the diff. `.factory/run/` is factory scratch and is git-ignored.

## Tasks and memory

- Work is filed as [beads](https://github.com/gastownhall/beads) in `.beads/`: `bd ready` lists what is actionable, `bd show <id>` reads one issue.
- The software factory claims and closes beads itself, so do not open, re-assign, or close them by hand during a run.
- Leave `bd remember "..."` notes only for what the code cannot tell a reader: a decision and its reason. Anything the tree already states belongs in a comment beside it, not in memory.

## Conventions

- **Core-purity seam:** `allesbuien-core` is platform-independent pure Rust with zero CXX, CXX-Qt, or Qt dependencies. Qt objects, timers, threads, image delivery, and process adapters belong in `app`.
- **Dependency injection:** Keep network and notification side effects behind the object-safe `FeedApi`, `RadarApi`, `IconSource`, and `Notifier` traits. Pass services, paths, location, and timer intervals through the existing construction seams; do not introduce globals. `bin/check-fast` holds the line textually: `side-effect seams` allows each process, environment, HTTP-client, and runtime constructor, and process-global mutable state, only in the files its table names, and `trait surface` refuses a trait wider than four methods; clippy's `excessive_nesting` (threshold 6, in `clippy.toml`) bounds block nesting. They are proxies for dependency inversion, interface segregation, and simplicity, not proofs.
- **Fakes over mocks:** Tests use small deterministic fake trait implementations with call counters or in-memory values; they never hit production networks or mutate process-global environment state. A fake several GUI harnesses need lives in `allesbuien-testkit`, so no harness has to silence a dead-code warning for the doubles it does not use; a fake one harness scripts stays beside the assertions it serves, as a private module under `app/tests/` if it is large enough to want a name.
- **Waiting on Qt:** GUI harnesses wait with `pump_until(condition, budget, attempt)` from `allesbuien-testkit`, never a hardcoded spin count. An iteration cap cannot tell falling out of the loop from succeeding in it, so an unreachable condition surfaces as whichever later assertion happens to read the unfinished state.
- **Qt threading:** HTTP, cache I/O, and notification dispatch run off the Qt thread; QObject changes return through the CXX-Qt thread queue. The only files read on the Qt thread are the two the 2-second polls read, both small and local: `ThemeController::poll` reads the theme's `colors.toml`, and each bridge's `poll_location` reads `weather.json`.
- **Theme-watch re-arm:** Poll `~/.local/state/omarchy/current/theme` every 2000 ms, re-resolving the path on each changed read and tolerating disappearance. Omarchy replaces that directory by removing and renaming, which no inode-bound watcher survives.
- **Theme fallback:** Rust exposes `themeAvailable`; QML uses `SystemPalette` when unavailable. Theme colours otherwise come from the controller. The error role is the exception: `SystemPalette` has none, so `Theme.qml` falls back to the literal `"red"`, the one literal colour `bin/check-fast`'s colour gate allows.
- **Location following:** Poll `~/.local/state/omarchy/settings/weather.json` every 2000 ms and never watch it — it is a desktop-wide setting that `omarchy-weather-location` rewrites and `--clear` unlinks. `LocationSettings` holds the inputs rather than the answer, and the weather and radar bridges each re-resolve and compare against the location they last adopted, so there is no shared cell to race and the order of the two `pollLocation()` calls carries no meaning. An `ALLESBUIEN_LAT`/`ALLESBUIEN_LON` pair is captured once at construction and outranks every later file change; `core/src/location_settings.rs`'s module doc argues all three points.
- **No location auto-detection, deliberately:** A missing `weather.json` falls back to Amsterdam-West, labelled as a default by `core/src/location_notice.rs`, and never to IP detection: this app draws Dutch radar and only Dutch radar, so a detected Berlin would be a confident-looking window over a permanently empty map. A name-only entry such as `--set Malibu` carries no coordinates and counts as no setting, because inventing them would be a second source of truth for a setting the desktop owns. README.md's *Location* section states the divergence from Omarchy's own widget in full.
- **Radar coverage:** A location outside `core/src/radar_projection`'s bounding box gets no marker and a stated notice, because a raster that paints its base and nothing else is indistinguishable from a failed frame request. The bounds are named once in `allesbuien-core`, in `radar_projection`, and `location_notice` asks that module rather than restating them; `assets/gen-basemap/src/transform.rs` keeps the generator's own copy, which has to move with them.
- **Radar delivery:** Metadata `times[]` determines frame order and cadence. Transparent frame PNGs are served without Rust-side composition through generation-keyed `image://radar/<generation>/<index>` URLs. The rain graph's end decides how many of them play, and every one still downloads.
- **Radar reach:** The animation ends on the rain graph's last bar. The weather bridge publishes that bar's moment as `rainEndLabel`, read the way the cursor reads the series (`rain_cursor::series_end`); `Main.qml` hands it to the radar bridge's `trackRainEnd`, and `core/src/rain_reach.rs` decides how many of the run's frames `frameCount` and `timestamps` expose, so looping, the slider, End, and the observed/forecast divider follow. Every frame still downloads and stays in the image store, so a later end brings a hidden frame back without a fetch or a new generation. The frames before the graph always stay, and an end that is missing, or that reaches none of the run's predictions, cuts nothing, so a run is never emptied; a failed weather refresh keeps its graph, and so its end. A new end is stored at once and applied on the next turn of the event loop, through the radar's own thread queue, never inside the weather bridge's refresh, because the frame it moves is handed straight back to that bridge.
- **Icon delivery:** Condition icons never hold the weather text back. A refresh publishes the icons already on disk, then the text, then downloads the rest, re-publishing after each one. A provider URL is withheld as `""` until the store can serve it, so each re-publish is a change QML reacts to, and each slot's loading state (`heroIconLoading`, the `iconLoading` role) follows only its own key's download, counted per refresh, so a pending slot shows a skeleton and a failed one stays empty. The payload a refresh queues carries that refresh's generation and is dropped once a later refresh has been adopted, so a fetch that is overtaken cannot put its older payload back; the per-key counts are deliberately not tagged that way, because a download that has started has to be counted out again whoever started it.
- **Error UX:** Retain last-good data and expose one minimal inline status per view. Malformed or missing optional input must not panic.
- **GUI tests:** Every file directly under `app/tests/` contains exactly one GUI test and constructs exactly one `QGuiApplication`, giving each Qt application its own process. A second test in the same file meets a `QGuiApplication` that already exists and dies with a SIGSEGV that reads like a product bug.
- **Module size:** No tracked `.rs` file exceeds **250 pure lines** — non-blank, non-comment, measured by `grep -cvE '^[[:space:]]*(//|$)' <file>` and enforced by `bin/check-fast` — because past that a module has outgrown one reviewer's working memory and is doing more than one thing. One number governs the whole tree, GUI harnesses included; `bin/check-fast`'s comment records why they lost their exception. The number is a symptom and cohesion is the goal, so the only sanctioned fix is extracting a module with a name describing one responsibility, its own doc, and its own tests.
- **Toolchain and gates:** Use pinned Rust 1.98.0. `bin/test` is the source of truth for workspace verification, keeps core coverage at or above 90%, and runs `bin/check-fast` first, `bin/check-qml-contract` after the build it reads, and `bin/check-gates` last, for reasons its own comments give. A gate that cannot be watched to fail is a decoration, so `bin/check-gates` replays every fixture in `tests/gates/` on each run and asserts that a red fixture's gate goes red **with the message that names the offender** and a green one's stays green; ship a fixture with any new gate or excuse it by name in `tests/gates/uncovered`, which `bin/check-fast`'s `gate coverage` gate enforces in both directions, and read `tests/gates/README.md` for the count and the per-gate argument.
- **Git in another repository:** in a linked worktree, where the factory's builders commit, git hands every command it runs there — the pre-commit hook, an alias, `git rebase -x bin/test` — `GIT_DIR`, and the hook `GIT_INDEX_FILE` too, both naming the worktree's repository. A gate script that runs git anywhere else, as `bin/check-gates` does in its scratch, reads its own repository first, with them, and then unsets what `git rev-parse --local-env-vars` lists, as githooks(5) says, whichever of them is set: `git rebase -x` hands `GIT_DIR` alone in a linked worktree and only `-c` options, as `GIT_CONFIG_PARAMETERS`, in the main checkout, and a commit made without `-c` options leaves `GIT_CONFIG_PARAMETERS` unset, so clearing them only when one is set keeps the others. With them, its `git init` marks the worktree's repository bare, which locks the main checkout out of every command that needs a work tree, and its commits land on the worktree's branch. The main checkout is no exception: there git sets no `GIT_DIR`, but a commit with `-a` or of named paths hands the hook an absolute `GIT_INDEX_FILE`, the commit's own index, so a scratch `git add` writes the scratch's files into it, and the commit fails on an object only the scratch holds or, when the repository already holds every object it names, goes through with what the scratch staged: a commit of `README.md` whose hook ran the runner on `omarchy-plugin-entry-point-missing` deleted `plugin/BarWidget.qml` as well. Such a script's commits in a repository of its own run no hook: clearing git's variables cannot stop a hook the global config names, and a global lefthook setup would run that repository's own `lefthook.yml` there. They look for their hooks in `/dev/null` (`-c core.hooksPath=/dev/null`), which stops the hooks a hooks directory holds, and set `hook.<event>.enabled=false` for each event a commit runs, which stops a hook a config defines by name (`hook.<name>.command`): git 2.55.0 runs one of those whatever `core.hooksPath` says, whether the global config defines it or the config `git init` copies from an `init.templateDir`. `bin/check-worktree-hook` runs `bin/check-fast`, `bin/check-gates` and itself, since `bin/test` runs it too, four ways against a decoy, each of the three variables the only one set in one of them: in a linked worktree with the index and `-c` options `git commit -a` hands the hook there, in the main checkout with the index alone that `git commit` with paths hands it there, in a linked worktree with `GIT_DIR` alone, as `git rebase -x` hands it, and in the main checkout with the options alone, as `git rebase -x` run with `-c` options hands it there. It runs them under a global config whose pre-commit and prepare-commit-msg hooks, in its hooks directory and defined by name, fail any commit that runs them, `--no-verify` or not, since that skips pre-commit alone of the two, and whose `init.templateDir` puts both kinds into every repository `git init` makes, so a commit that reads no global config still meets them, and refuses a failure, any change to the decoy, and a git command run with those options; a new script that runs git elsewhere joins its list.
- **CXX-Qt name binding:** Every `extern "RustQt"` block carries `#[auto_cxx_name]`, with no exceptions, so multi-word members reach C++ in the camelCase QML reads them by. Without it nothing fails to compile and no test fails; the window simply comes up unthemed and unbound. `bin/check-fast` asserts the source shape and `bin/check-qml-contract` asserts the generated type registry still answers every member name `app/qml` asks for.
- **Clock-reading tests:** `core/src/radar_timeline.rs`, `core/src/datetime.rs`, and `core/src/radar_transport.rs`, which hands `Timestamp::now()` to the run-freshness check, read the host clock on purpose, so banning `now()` would condemn the wrong lines. Tests have to hold in any zone instead, and `bin/test` re-runs the suite under UTC, `Asia/Kolkata`, `Pacific/Auckland`, and `America/New_York` to prove it — Kolkata's half-hour offset being what catches an assertion that pinned the minutes to `:00`.
- **Packaging:** `pkgver` is static. The canonical package build is exactly `(cd pkgbuild && makepkg -f)` as invoked by `bin/install`, `just package`, and automation.
- **Third-party notices:** `pkgbuild/THIRD-PARTY-LICENSES` is what cargo-about writes from `Cargo.lock` with `pkgbuild/about.toml` and `pkgbuild/about.hbs`: generated, committed, and never edited by hand. Regenerate it from the repository root with `cargo fetch --locked && cargo about generate --frozen --fail -m app/Cargo.toml -c pkgbuild/about.toml -o pkgbuild/THIRD-PARTY-LICENSES pkgbuild/about.hbs` and the cargo-about `.cargo-about-version` names, which `mise.toml` pins too; `bin/test`'s `third-party notices` gate regenerates it the same way and refuses any difference. `about.toml`'s `accepted` list is both the licence allowlist and the election order: a crate is listed under the first licence it allows, Apache-2.0 first because its text names nobody, and a crate that allows none stops the generation by name. The template prints no versions, so a bump that changes no crate and no licence text leaves the file byte for byte as it was. cargo-about reads licence files and never source-file headers, so `about.hbs` keeps the notices in headers by hand: ring's and rustls-webpki's ISC copyright holders, futures-channel's two-clause BSD queue header in full, and the copyright of the C++ original that zmij is a line-by-line port of. `third-party notice coverage` reads the headers of every crate `cargo tree` says the binary links, and refuses a holder on no `Copyright` line of the notices, a BSD-style header whose text they do not reproduce, and a linked crate their index leaves out. The standard library's notice is not generated: `package()` copies the building toolchain's `COPYRIGHT-library.html` beside the file, and `bin/check-fast`'s `shipped notices` gate keeps both install lines and refuses a placeholder copyright line.
- **Attribution:** Buienradar free data is for non-commercial use with attribution, and the terms name exactly two visible obligations: the words `Buienradar.nl` are shown, and they link to the root domain `https://www.buienradar.nl`. Keep both in the app and in the README. Any label wrapped around them is ours to word or drop; the GUI test asserts the domain text and the link, not a sentence.
- **Omarchy plugin is a launcher:** the widget launches or focuses the app, and installs or updates the release `plugin/release.sha256` pins, and nothing else. Every decision and install step lives in `plugin/widget.sh`, run through the same `bash -lc` login shell `bar.run` uses, so both see `~/.local/bin`; `BarWidget.qml` maps the probe's exit code onto the button — 0 launch or focus, 10 install, 11 absent with nothing it can install, 12 update ready, and any other code a failed probe, which dims the icon and opens the floating terminal as 11 does but whose tooltip says the check failed — and `tests/widget/run.sh` proves the script against fakes; the test-only `allesbuien-widget-tests` crate runs it, and shellchecks the scripts, inside `cargo test --workspace`, so `bin/test` and CI hold the widget to it. Each click acts on a probe completed after the click, never on a remembered state, and the only other probes are the one on load and one every 5 s while the app is known to be absent (10 or 11), never while a probe fails. Ownership is asked as membership of the resolved binary in a captured `pacman -Qlq allesbuien`, never with `pacman -Qo`, which reads every installed package's file list and took over a second on an unowned binary, on a probe that runs at every click. Only an `allesbuien` package older than the pin by `vercmp` is updated: a binary another package owns, one pacman does not own, such as a Mode B install, and an equal or newer version are launched and left alone, so a click never downgrades. An installed version pacman cannot report stops the click rather than counting as older, and so does an `allesbuien` package pacman records with no `allesbuien` on PATH, which a fresh install could downgrade. A click that installs downloads over HTTPS into a private temp dir, checks the file against the pin with `sha256sum --check`, checks the `qt6-declarative` its `.BUILDINFO` records against the installed one, takes the sudo password with `sudo -v`, and decides again, because a second click or another installer can change what is installed while it downloads or while the prompt waits; only if the answer still holds for the same pin line does it run `sudo pacman -U --needed` in Omarchy's floating terminal, whose prompt is the consent. pacman holds its database lock from then until it commits, and has no flag that refuses a downgrade, so the last decision comes after every wait the person controls, and `--needed` skips a package that became the pinned version in the instant before pacman took its lock; nothing is ever piped into a shell. The script runs there under `bash -l`, because the terminal inherits the app launcher's environment rather than the one the probe saw, and both `bar.run` strings go through Omarchy's `Util.shellQuote`, the install one twice, once for `bar.run`'s shell and once for the shell the terminal wrapper splices it into. The Qt check goes on only if the installed upstream version is the same or newer by `vercmp`: an older one stops the click before any password prompt and points to `omarchy-update`, and a version that cannot be read, or a comparison `vercmp` does not answer with -1, 0, or 1, stops it too, since an unknown version or order must never count as new enough. The app compiles its QML ahead of time, so its binary binds Qt's private API and need not start on an older Qt, and a versioned `depends` in the PKGBUILD would instead let `pacman -U` upgrade Qt alone, a partial upgrade, underneath the running shell. The widget never asks GitHub which release is the latest. No fetching, parsing, version, or theme logic in plugin QML, the strip of its own URL that finds `widget.sh` excepted — `bin/check-fast`'s colour gate reads `plugin/*.qml` too, so a literal colour is refused, but no gate enforces the rest. Its glyph is one static Nerd Font codepoint in the bar's font, never an image and never a weather symbol, because the Omarchy pill beside it already shows the condition and a second cloud or raindrop would read as a duplicate. Entry points must be tracked files and the tree may hold no symlink, because `omarchy plugin add` refuses one. It never names `omarchy.weather` in `clonedFrom`, so it coexists with the built-in pill instead of replacing it.
- **Release pin:** `plugin/release.sha256` is one line in `sha256sum --check` format, a SHA-256 digest, two spaces, and the asset name `allesbuien-<version>-<pkgrel>-x86_64.pkg.tar.zst`, and it is the only copy of that digest anywhere; the widget derives the version, the tag, and the download URL from the name. It is written only after a release is published, by `bin/pin-release`, which refuses a draft or a release that is not immutable, since either's asset could still be replaced under the pin, takes the digest GitHub records for the asset, checks it against a download made through `gh`, authenticated so that it works while the repository is private, and leaves the commit to the releaser. So the pin may lag the version surfaces between a bump and that commit, and the widget suite's `committed-pin` case allows the lag, and no pin at all before the first pin commit, but refuses a pin the widget cannot use or one ahead of `app/Cargo.toml`. `omarchy plugin add` and `update` install `main`'s current HEAD, not the marketplace's verified snapshot, so treat every push to `main` as shipped to plugin users. Decided 2026-10-10: AUR account registration is closed indefinitely, so `allesbuien-bin` cannot be published, and rather than wait on it the widget installs and updates straight from the GitHub release, verified against the committed pin. The AUR comes back later as an additional channel, not a dependency, with its recipe in the AUR repo rather than here; `pkgbuild/PKGBUILD` stays the source-less local recipe. README's *Releasing* section gives the order: land, plugin checks, immutable releases on, signed tag on the checked commit, draft release inspected and its package smoke-tested, release published and checked immutable, pin commit, plugin checks and click-through once `main` carries the pin, make the repository public, dry run, submit while `main`'s HEAD is the pin commit, or a later one that leaves `manifest.json`, `plugin/` and the root `.gitattributes` as it left them and passes `omarchy plugin validate` on a fresh clone (a first listing takes no SHA).
- **Release surfaces:** nine files carry the version, listed by path in README's *Releasing* section; `release.yml` checks three of them against the tag, and `bin/check-fast`'s `release version` gate holds all nine to `app/Cargo.toml` on every commit. `CHANGELOG.md`'s section for a version is the text of its tag annotation.

## Anti-Patterns

- Do NOT add CXX, CXX-Qt, Qt, app-thread, or UI dependencies to `allesbuien-core`.
- Do NOT put domain or business logic in QML, controller C++, or the image-provider trampoline. The sole C++ carve-out is the existing construction/bridge surface; keep it minimal and logic-free.
- Do NOT block the Qt thread on HTTP, filesystem work beyond the two polls' small reads, notification dispatch, or Tokio futures.
- Do NOT construct controllers outside the existing library bootstrap/injection seams or introduce global service state.
- Do NOT use mocks when a trait fake can express the scenario; do not call live endpoints from unit tests or mutate process-global environment variables in tests.
- Do NOT place multiple GUI tests or multiple `QGuiApplication` instances in one integration-test file/executable.
- Do NOT decode or compose radar/basemap images in Rust, hardcode radar cadence, retain stale generations, or allow an unbounded radar cache.
- Do NOT use a file/inode watcher for the Omarchy theme directory or the Omarchy weather settings file, fabricate fallback palette values, hard-fail on missing theme keys, or add custom C++ watcher bindings.
- Do NOT add IP geolocation, forward or reverse geocoding, or an in-app location picker. The desktop already ships `omarchy-weather-location`, and a second way to set a desktop-wide setting is the thing to avoid; the divergence from Omarchy's IP auto-detection is a recorded decision, not an omission.
- Do NOT hardcode colours in QML; bind controller theme properties or `SystemPalette` fallback values. `Theme.qml`'s `"red"` error fallback is the one exception.
- Do NOT add toast/retry frameworks or notification spam; keep one inline error status per view and one announcement per spell of rain.
- Do NOT replace Buienradar with wttr.in/Open-Meteo, expand beyond Dutch radar, or remove the required attribution: the visible `Buienradar.nl` and its link to `https://www.buienradar.nl` both have to stay.
- Do NOT copy a `map-nl-*` image from another project, any unlicensed basemap, or OSM tile-server imagery. Basemaps come only from the pinned Natural Earth public-domain sources through `assets/gen-basemap`.
- Do NOT write to another project's checkout beside this one, add AllesBuien to a repository that encloses this directory, or modify `/usr/share/omarchy`.
- Do NOT turn the app into a Quickshell widget; the bar widget under `plugin/` launches, focuses, installs or updates the pinned release, and must stay that thin. Do NOT touch built-in `omarchy.weather` or add a server/deploy/Docker surface. Installing and updating from the GitHub release against the committed pin is a recorded decision of 2026-10-10, and publishing `allesbuien-bin` to the AUR later, as an additional channel, one of 2026-09-18; neither violates this line.
- Do NOT create `.SRCINFO`, an AUR remote, a dynamic `pkgver()` function, network-backed sources, or alternative package-build invocations **in `pkgbuild/`**; the AUR clone outside this tree is the one place those belong.
- Do NOT run `makepkg -s`, `makepkg -i`, `makepkg -si`, or `makepkg -fsi`; only `(cd pkgbuild && makepkg -f)` is sanctioned.
- Do NOT invoke bare `sudo` or any command that can wait for a password. Live install mode is user-scope Mode B unless that recorded decision is explicitly changed; `bin/install` hardcodes it, printing `INSTALL MODE: B` and the Mode B command for a person to run. This governs agents and `bin/install`. The widget's install and update click, which runs `sudo pacman -U` in Omarchy's floating terminal, the README's `sudo pacman -U` lines, and `just install` are commands a person runs at their own terminal, so an agent exercising the widget swaps its `sudo -v` and both `sudo pacman -U` calls in its throwaway copy of `plugin/widget.sh` for an inert echo rather than clicking the real one.
- Do NOT meet the module-size budget by compressing formatting: joining statements onto one line, deleting blank lines, or removing doc comments to get under the number is a defect, not a fix. Comments and blank lines are not counted precisely so that explaining the code is always free. If a file has no honest cohesive seam, leave it over budget, raise its documented limit deliberately, and write down why.
- Do NOT write build outputs or package artifacts outside ignored paths.
- Do NOT use mutable GitHub Action references such as tags or branches; pin every third-party action to a full 40-character commit SHA and record the release tag in a comment.
- Do NOT use pre-release Qt Rust bridges, qmetaobject-rs, or mix CXX-Qt family versions; the workspace pins the complete 0.10.0 family.
- Do NOT reduce agreed scope behind “MVP” or “phase 1” language, and do not port third-party source code; external projects are pattern references only.
- Do NOT edit `.factory/gate`, `.factory/protected`, or the paths that file lists — the gate body, `tests/gates/uncovered`, the workflows, `deny.toml`, `pkgbuild/about.toml` and `pkgbuild/about.hbs`, whose accepted licences and hand-kept notices no gate can judge, the justfile and any `.just` module, mise's and lefthook's config files with any link that would hand either tool one from elsewhere, and the root `.gitignore`, whose re-includes keep a global ignore from hiding a local one. Weakening a check is the one change no check can catch, so those diffs are read by a human rather than approved by a run. The config files steer the pre-commit hook every worktree shares: a copy that drops `no_auto_install` or the postinstall's guard, or a `lefthook-local` file that turns `no_auto_install` off, rewrites that hook for every checkout at its next commit or `mise install`.
